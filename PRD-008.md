# PRD-008 — Local Operator Inbox for WhatsApp Dating Agent

**Status:** Ready for engineering implementation, subject to repository inspection  
**Priority:** High  
**Platform:** macOS, local Next.js application  
**Database:** Existing SQLite database  
**Primary user:** Mike  
**Release:** V1 — strictly read-only

---

## 1. Product objective

Build a small, local web application that provides a clear operational view of the existing WhatsApp dating agent.

The dashboard must answer five questions:

1. Which contacts is the bot managing?
2. What has been said in each conversation?
3. Which AI replies were generated, and why are they relevant to that point in the conversation?
4. Which drafts are currently actionable, stale, superseded, or sent?
5. What did the bot actually do after Mike approved a reply?

**The product is an operator inbox, not another WhatsApp client.**

The existing WhatsApp bot remains responsible for receiving messages, generating drafts, processing voice feedback, approving options, and sending messages.

The dashboard observes those operations. It must not perform them.

### Success definition

Mike can open a local browser, select a contact, read the WhatsApp conversation and associated AI drafts, and understand the current state of that contact without searching through Message Yourself notifications.

The dashboard must achieve this without introducing another source of truth or changing the bot's behavior.

---

## 2. Architectural constraints

These are non-negotiable.

- Keep the existing SQLite database as the only persistent source of conversation and draft data.
- Do not migrate to MySQL, PostgreSQL, Firebase, or another database.
- Do not create a second persistent copy of messages or drafts.
- Do not change the bot's existing sending or approval logic.
- Do not instantiate the existing `Store` class from the dashboard if it performs migrations or writes during initialization.
- Do not run migrations or modify the database schema.
- Do not write to the database from the dashboard.
- Do not introduce a separate bot API, WebSocket service, synchronization daemon, or message broker.
- Do not connect the dashboard directly to WhatsApp.
- Do not introduce user accounts, cloud hosting, analytics, or external monitoring.
- The dashboard must operate locally on Mike's Mac.

Use Next.js App Router, React, and `better-sqlite3`, unless repository inspection reveals a compelling compatibility problem.

Prefer the smallest implementation that satisfies the requirements.

## 4. Application architecture

The intended architecture is:

```text
WhatsApp Web
     |
     v
Existing Node.js bot
     |
     | sole application writer
     v
data/whatsapp.db
     ^
     | read-only SQLite connection
     |
Local Next.js server
     |
     v
Browser at 127.0.0.1
```

### 4.1 Database access

Create a dedicated server-only database reader.

The reader must:

- Accept an explicit absolute database path.
- Verify that the database file exists before opening.
- Open it using `better-sqlite3` with `readonly: true`.
- Set `PRAGMA query_only = ON` as an additional safeguard.
- Never import or instantiate the writable `Store`.
- Never execute SQL that mutates persistent state.
- Never alter WAL settings or perform checkpoints.
- Never perform schema migrations.
- Use parameterized SQL for all externally supplied values.
- Avoid verbose SQL logging that could expose personal information.

Example connection pattern:

```ts
import "server-only";
import Database from "better-sqlite3";
import { statSync } from "node:fs";

const path = process.env.WHATSAPP_DB_PATH;

if (!path) {hrow new Error("WHATSAPP_DB_PATH is required");
}

if (!statSync(path).isFile()) {
  throw new Error("Configured SQLite path is not a file");
}

const db = new Database(path, {
  readonly: true,
  timeout: 1000
});

db.pragma("query_only = ON");
```

The code is illustrative; adapt initialization and error handling to the actual repository.

Use one reusable read-only handle per server process rather than constructing a connection for every rendered component.

### 4.2 WAL behavior

The existing bot is the only logical writer.

SQLite WAL allows concurrent readers and a writer, subject to locking and checkpoint conditions.

The dashboard must:

- Execute short, bounded queries.
- Never hold a read transaction open for the duration of a browser session.
- Complete any transaction before rendering or awaiting unrelated asynchronous work.
- Handle temporary `SQLITE_BUSY` failures gracefully.
- Never attempt to repair WAL files or change journal mode.
- Work when new bot messages are committed while the dashboard is open.

If `-wal` or `-shm` files are missing or inaccessible, show a useful local configuration error. Do not copy or replace the database as a workaround.

### 4.3 No additional persistent store

Do not use browser local storage, IndexedDB, or another database to maintain copies of conversations.

Transient UI state—selected filters, temporary scroll position, current expanded draft—is acceptable.

## 5. Navigation and layout

### 5.1 Primary screen

Use a two-column operator layout.

**Left column: Contact inbox**

Approximately 300–360 pixels wide on a normal desktop screen.

**Right column: Selected conversation**

Uses the remaining width and contains messages and associated draft activity.

A compact application header displays:

- `Agent Inbox`
- `Local · Read only`
- Last successful refresh time

Do not display a green online indicator unless actual bot connectivity is persisted and verified. Contact enablement is not proof that the WhatsApp connection is online.

### 5.2 Contact URLs

Every coust have a stable, directly accessible URL.

Preferred route:

`/inbox/[contactKey]`

Use an existing non-sensitive stable contact identifier if available. Otherwise derive a deterministic URL-safe key from the canonical `chat_id` without changing the database.

Avoid exposing raw phone numbers in URLs when practical.

The server must resolve each route to a canonical contact that actually exists in the database.

Unknown contact keys return a not-found view.

Do not accept arbitrary SQL identifiers or filesystem paths from route parameters.

### 5.3 Responsive behavior

Prioritize a MacBook-sized desktop screen.

At narrow widths, show the contact list and conversation as separate views with a clear back button.

Do not build a separate mobile application.

## 6. Contact inbox

Each contact row should contain:

**Primary line**

Display name, using the best existing persisted contact label.

**Secondary line**

Phone number if available and permitted by the existing data model.

**Activity preview**

Last persisted message, truncated to one or two lines.

**Status**

`Enabled` or `Paused`, based on persisted contact state.

**Draft indicator**

Show `Draft ready` only when an actually actionable draft is persisted.

### 6.1 Sorting

Default to most recently active contact first.

Use the most recent persisted conversation activity according to the inspected schema.

Contacts without messages remain visible below active conversations.

### 6.2 Contact identity

Use `chat_id` as the canonical identity where the existing bot does so.

Phone-number aliases and LID identifiers must not create duplicate inbox rows.

Do not merge two contacts merely because their display names match.

### 6.3 Inbox indicators

Distinguish contact status from draft status.

For example:

- `Enabled` — bot is permitted to manage this contact.
- `Paused` — persisted contact state is disabled.
- `Draft ready` — a current actionable draft exists.
- `No active draft` — no actionable draft is recorded.

Do not introduce an `Unread` count unless the bot already persists read state.

Do noy `Generating` simply because a recent incoming message exists. Show that status only if generation progress is actually persisted.

### 6.4 Contact count and pagination

Initially display a bounded list, such as the 50 most recently active contacts.

If more contacts exist, provide a simple mechanism to access older entries.

Avoid loading the entire message history to calculate contact previews.

## 7. Conversation thread

The conversation should resemble a readable messaging timeline, but not attempt to duplicate the entire WhatsApp interface.

### 7.1 Required content

Display persisted messages in chronological order.

For each message, show:

- Actual text, if present.
- Incoming or outgoing direction.
- Timestamp.
- Sender context when necessary.
- Message type, when known.

Use different visual alignment or styling for incoming and outgoing messages.

Avoid elaborate chat bubbles or avatars that consume space without adding information.

### 7.2 Voice messages

If the database contains a voice message and its transcription, display the transcription with a clear indication that it came from audio.

If the transcription is pending or unavailable, do not invent it.

Example:

`Voice note · Transcript unavailable`

Do not implement voice playback unless the existing schema and stored media make this straightforward and safe. It is not required for V1.

### 7.3 Images and other attachments

Display lightweight placeholders for message types whose content cannot be rendered directly.

Examples:

- `Image received`
- `Audio message`
- `Document attached`

Do not load remote media URLs or expose local attachment directories through a generic filesystem route.

Media rendering is outside V1 scope.

### 7.4 Message ordering

Use persisted timestamps with a stable secondary identifier.

Equal timestamps must not cause unstable ordering.

Messages loaded through pagination must not appear twice.

### 7.5 Pagination

Load a bounded number of recent messages initially, approximately 75–100.

Provide `Load earlier messages` using stable cursor-based pagination where the exing schema supports it.

Do not load years of history on every refresh.

## 8. AI draft timeline

**This is the application's most important feature.**

The UI must show AI suggestions in the context of the conversation.

WhatsApp already shows messages. It does not clearly show which drafts were generated, revised, rejected, or superseded.

This is the dashboard's primary additional value.

### 8.1 Draft presentation

Each draft set should appear as a distinct panel associated with its chronological position.

Show:

- Draft ID.
- Creation timestamp.
- Actual persisted status.
- Three option labels.
- Spanish text for each option.
- English translation for each option.
- Selection or approval information, if persisted.
- Revision or supersession information, if persisted.

Preserve the existing three-option order:

1. Natural
2. Playful
3. Direct

The panel must not be interactive in V1.

### 8.2 Draft-to-message relationship

Use an explicit stored triggering-message relationship if one exists.

If no such relationship exists, insert draft activity into the chronological timeline based on its recorded creation time.

In that case, label it by creation time and draft ID; do not claim that a particular message triggered the draft.

Do not construct an invented `trigger_message_id` or store a guessed relationship.

### 8.3 Draft lifecycle

Inspect the existing implementation and map actual persisted statuses to clear presentation labels.

Candidate concepts include:

- Created.
- Active / ready.
- Revised.
- Superseded.
- Stale.
- Approved.
- Submitted for sending.
- Sent.
- Failed.

**These are concepts, not permission to invent new database states.**

Only display lifecycle transitions that are supported by the existing persisted data.

If the database stores only the latest status, show that status. Do not fabricate a historical sequence.

### 8.4 Approved option

If the bot persists the approved option number, visually distinguish the selected option.

Do not determine the selected option by comparing the outgoing WhatsApp text to the three generated options.

Text matching can be ambiguous, especially when messages have been revised or manually edited.

If the selected option is not recorded, show the outgoing message separately without claiming which option produced it.

### 8.5 Sent versus delivered

Do not confuse these states:

- Mike approved a draft.
- The bot attempted to send.
- WhatsApp accepted the send operation.
- WhatsApp delivered the message.
- The recipient read the message.

Only present the strongest state supported by persisted evidence.

If the existing bot records a successful `sendMessage` call but no delivery receipt, label the result `Sent` or `Submitted`, according to the bot's existing semantics. Do not display `Delivered` or `Read`.

### 8.6 Stale drafts

If a draft is marked stale or superseded by the bot, visually distinguish it from actionable drafts.

Do not allow the UI to decide independently that a draft has become invalid.

For instance, a newer incoming message may be shown after a draft, but that observation alone must not overwrite or reinterpret the bot's persisted status.

### 8.7 Draft revisions

Where the database preserves revisions, show the old draft and replacement in chronological order.

A compact relationship such as `Revised from #32` is useful when backed by a real stored reference.

If voice feedback is saved, show its persisted transcript as a feedback event when feasible.

Do not imply a revision history exists if only the final draft was saved.

## 9. Data presentation contract

Create a small server-side adapter that converts existing SQLite rows into presentation-friendly objects.

This adapter must be read-only and contain no business decisions about sending or approving messages.

Suggested conceptual types:

```ts
type InboxContact = {
  key: string;
  displayName: string;
  phoneNumber?: string;
  enabled: boolean | null;
  lastActivityAt: string | null;
  lastMessagePreview: string | null;
  hasActionableDraft: boolean;
};

type ConversationEvent =
  | {
      kind: "message";
      id: string;
      timestamp: string;
      direction: "incoming" | "outgoing" | "unknown";
      messageType: string;
      text: string | null;
    }
  | {
      kind: "draft";
      id: string;
      timestamp: string;
      status: string;
      options: DraftOption[];
      selectedOption: number | null;
      relatedMessageId: string | null;
      previousDraftId: string | null;
    };

type DraftOption = {
  style: string;
  label: string | null;
  replyEs: string;
  translationEn: string | null;
};
```

These are UI types, not proposed database tables or migration definitions.

Fields may be nullable or unavailable depending on the actual schema.

### 9.1 Malformed data

The UI must remain usable if:

- A contact has no display name.
- A message has no text.
- A voice transcription is missing.
- A draft contains malformed JSON.
- A draft has fewer or more than three persisted options.
- A draft references a missing older message.
- A contact has no message history.

Display a restrained placeholder or data warning rather than crashing the entire inbox.

Do not silently synthesize missing options or translations.

## 10. Refresh and freshness

### 10.1 Refresh approach

Use client-side polling to refresh server-rendered data approximately every four seconds.

A small Client Component may use `router.refresh()` to request updated Server Component content.

No WebSockets, Socket.IO, message bus, or custom synchronization service.

### 10.2 Polling rules

- Refresh only while the dashboard is open and the tab is visible.
- Trigger a refresh when the tab becomes visible again.
- Avoid overlapping refresh requests.
- Keep the selected contact unchanged.
- Keep expanded draft panels unchanged.
- Preserve manual scroll position.
- Do not jump the user to the newest message while they are reading older content.
- If the user is already near the bottom, following new messages automatically is acceptable.

### 10.3 Next.js caching

The implementation must ensure live SQLite reads are performed at request time rather than returning a cached page.

Choose the appropriate dynamic-rendering mechanism for the installed Next.js version.

Do not rely on `router.refresh()` alone to overcome a server-side cache.

Verify freshness through an actual database update while the page is open.

### 10.4 Refresh errors

If a read fails:

- Preserve the last successfully rendered content if practical.
- Display a small `Refresh failed` or `Temporarily unavailable` message.
- Continue attempting later refreshes.
- Never modify the bot's database or restart the bot automatically.

## 11. Privacy and security

This dashboard displays private WhatsApp conversations. Security is part of the feature, not optional polish.

### 11.1 Network binding

Bind explicitly to:

`127.0.0.1`

Do not bind to:

`0.0.0.0`

Do not deploy to Vercel, a public server, or a cloud environment.

Do not automatically enable Tailscale sharing, public tunnels, reverse proxies, or LAN access.

The intended user opens the dashboard in a browser on the same Mac as the bot.

### 11.2 Data exposure

- No telemetry or analytics service.
- No third-party session recording.
- No externally hosted fonts required.
- No external image requests using private message data.
- No cloud error reporting containing conversation contents.
- No logging of full messages, draft text, transcriptions, or private identifiers.
- No automatic exports.
- No browser-side persistence of conversation history.
- No publicly served SQLite, WAL, or SHM files.
- No service workers or offline conversation caches.
- Use `no-store` responses for private dynamic content where appropriate.
- Use normal React escaping for untrusted chat text; no raw HTML injection.

Use security headers appropriate to a localhost-only application, including protection against framing and unexpected external resource loading.

Limit accepted local hostnames and avoid trusting arbitrary forwarded host headers.

### 11.3 Localhost limitations

Binding to localhost prevents ordinary remote network connections. It does not make the dashboard inaccessible to other processes or users operating on the same computer.

V1 assumes Mike controls and trusts his local Mac session.

Do not claim the dashboard has strong authentication or encryption beyond what has actually been implemented.

### 11.4 Secrets

Do not expose WhatsApp credentials, session files, API keys, OpenRouter configuration, or application secrets through the UI.

The dashboard needs only database read access.

## 13. Future control architecture — not V1

The memo proposes a reasonable future direction for interactive controls.

If Mike later wants to approve drafts or pause contacts from the dasoard, the UI must not perform direct SQL updates.

Instead, the existing bot should expose a narrowly scoped localhost command interface that invokes its established application methods.

Any future command integration must preserve:

- Canonical `chat_id` routing.
- Contact enabled-state checks.
- Draft revision checks.
- Stale-draft protections.
- Exact approved-option selection.
- WhatsApp send authorization.
- Cross-contact isolation.
- Existing persistence and error handling.

A future command API would also require explicit local authorization and cross-origin request protections.

**Do not build this API now.**

## 15. Performance requirements

The dashboard should remain lightweight on an always-running Apple Silicon Mac with limited memory.

### Required practices

- Bound contact queries.
- Bound message-history queries.
- Use stable pagination.
- Select only fields the UI needs.
- Do not decode large media blobs during normal page rendering.
- Avoid loading all drafts for all contacts on every refresh.
- Reuse the SQLite reader connection.
- Keep database transactions short.
- Avoid unnecessary client-side hydration of large historical datasets.

Inspect existing indexes before writing queries.

Do not add indexes in V1 because that would violate the read-only, no-migration constraint.

If an existing table lacks an index necessary for acceptable performance, report the issue instead of silently modifying the database.

### Practical performance target

For a typical local inbox with dozens of contacts and a substantial message history:

- Contact switching should feel immediate.
- Recent conversation loading should normally complete in approximately one second or less.
- Refreshes should not produce visible flashing or layout resets.
- The dashboard should not noticeably slow message processing in the bot.

These are engineering targets to measure against the actual database, not guarantees.

## 16. Acceptance tests

The release is incomplete until the following tests pass.

### A. Read-only verification

1. Start the existing bot.
2. Launch the dashboard.
3. Open multiple contacts.
4. Refresh repeatedly.
5. Verify the dashboard has not modified any application tables.
6. Attempt an accidental write through the dashboard's database handle and verify SQLite rejects it.
7. Confirm the bot continues receiving and sending messages normally.

SQLite WAL bookkeeping may change independently during normal bot operation; the requirement is that the dashboard makes no application-data mutations.

### B. Contact identity isolation

1. Create or use two allowlisted contacts.
2. Receive separate messages from each contact.
3. Generate drafts in both conversations.
4. Confirm each inbox row points to the correct canonical `chat_id`.
5. Confirm each thread contains only its own messages and drafts.
6. Test phone-number and LID aliases if the real database contains them.
7. Confirm no duplicated contact is created for an alias.

### C. Reverse-order approvals

1. Generate draft A for contact A.
2. Generate draft B for contact B.
3. Approve draft B through the existing WhatsApp interface.
4. Approve draft A afterward.
5. Verify the dashboard shows the correct selections and persisted send results under their respective contacts.
6. Verify neither thread displays the other contact's draft or outgoing message.

The dashboard must never participate in the approval operation.

### D. Revision and stale-draft behavior

1. Generate a draft.
2. Revise it using the existing quoted voice-feedback workflow.
3. Confirm the dashboard shows the replacement and prior version when both are persisted.
4. Receive a newer incoming message that causes the bot to invalidate a draft.
5. Verify the dashboard reflects the actual persisted status.
6. Confirm it never presents a superseded draft as actionable.

### E. Live database updates

1. Keep the dashboard open.
2. Receive a new WhatsApp message.
3. Verify it appears automatically after a refresh.
4. Generate new draft options.
5. Verify they appear without a manual browser reload.
6. Pause the contact through the existing bot interface.
7. Verify the contact's enabled state updates.
8. Confirm viewing older messages does not cause the screen to jump to the bottom.

### F. Database error handling

Test:

- Missing SQLite path.
- Incorrect path.
- Bot temporarily stopped.
- Brief SQLite lock contention.
- Missing contact.
- Empty conversation.
- Malformed persisted draft options.
- Missing translation.
- Unavailable audio transcription.

Failures must not cause database creation, migrations, or bot restarts.

### G. Privacy verification

1. Verify the server is bound to loopback only.
2. Verify it is inaccessible from another device on the LAN.
3. Verify no remote analytics or logging endpoints receive conversation content.
4. Verify private messages do not appear in normal application logs.
5. Verify SQLite files and session credentials cannot be downloaded through HTTP.
6. Verify messages containing HTML-like strings are rendered as text rather than executable markup.

## 17. Definition of done

V1 is complete when:

- The local dashboard starts successfully.
- Existing contacts appear from the real SQLite database.
- A contact opens at a stable URL.
- Its messages appear in chronological order.
- Its AI draft options appear alongside relevant timeline activity.
- English translations and draft statuses are visible when persisted.
- New messages and draft changes appear through periodic refresh.
- Multiple contacts remain isolated.
- The existing bot works unchanged.
- No application-data writes occur from the dashboard.
- The application is accessible only locally.
- All required acceptance tests pass.

The dashboard does not need to be a polished consumer application. It does need to be a reliable, attractive, readable operator tool.
