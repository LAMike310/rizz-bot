# PRD-002: WhatsApp AI Conversation & Draft Engine

**Project:** WhatsApp Dating Assistant  
**Version:** 1.0  
**Status:** Ready for implementation  
**Priority:** P0  
**Deployment:** Local M1 MacBook  
**Dependency:** PRD-001 — WhatsApp Linked Device Connection

---

## 1. Executive Summary

Build a lightweight, locally hosted WhatsApp AI assistant that monitors an explicitly approved test conversation, maintains conversation history, and generates contextual Spanish reply suggestions using OpenRouter.

The assistant is intended eventually to help Mike communicate naturally with adult dating matches in Medellín and arrange in-person dates when interest is mutual.

Version 1 will operate exclusively in **DRAFT_ONLY** mode.

The assistant must never send messages automatically to the test contact. Instead, it will send generated draft notifications to Mike's own WhatsApp self-chat, allowing him to review, copy, edit, and manually send replies.

The system must prioritize three qualities:

1. **Simplicity:** Minimal dependencies, components, and configuration.
2. **Context accuracy:** Responses must reflect the latest complete conversation.
3. **Reliability:** No duplicate, outdated, or unintended messages.

### Core product principle

**One contact. One conversation history. One configurable model. One draft per completed incoming-message burst.**

Do not build features until they are needed.

## 2. Goals

### Primary goal

Demonstrate a complete working pipeline:

WhatsApp message → SQLite → 45-second debounce → OpenRouter → structured draft → WhatsApp self-chat.

### Secondary goals

- Preserve conversation history across application restarts.
- Maintain a consistent writing style using an editable prompt and user profile.
- Support changing OpenRouter models without changing application code.
- Prevent duplicate processing and stale drafts.
- Provide basic operational logging.
- Keep architecture extensible for future contact activation, calendar access, and selective auto-send.

### Success definition

Mike can use his secondary U.S. WhatsApp number to simulate a dating conversation.

After a message or series of messages arrives, the application waits 45 seconds after the last incoming message, generates one contextual Spanish reply, and delivers a reviewable draft to Mike's primary WhatsApp self-chat.

**The secondary number must not receive any automated reply.**

## 8. Database Design

Use one local SQLite database with three tables.

Enable WAL mode and foreign keys where applicable.

### 8.1 Contacts

```sql
CREATE TABLE contacts (
  chat_id TEXT PRIMARY KEY,
  phone TEXT,
  name TEXT,
  enabled INTEGER DEFAULT 0,
  revision INTEGER DEFAULT 0,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
```

Purpose:

- Identify the approved conversation.
- Control whether drafting is enabled.
- Track conversation revision numbers.

Only one contact may be enabled in V1.

### 8.2 Messages

```sql
CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  whatsapp_id TEXT UNIQUE NOT NULL,
  chat_id TEXT NOT NULL,
  direction TEXT NOT NULL,
  body TEXT NOT NULL,
  message_timestamp INTEGER,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_messages_chat
ON messages(chat_id, id);
```

Direction values:

- `incoming`
- `outgoing`

Requirements:

- Store only text messages from the approved test conversation.
- Use the WhatsApp message identifier to deduplicate events.
- Preserve the chronological order of messages.
- Store manually sent outgoing messages.
- Never store self-chat draft notifications as part of the dating conversation.
- Increment conversation revision only when a new message is successfully inserted.

The application must not silently treat a duplicate message as a new event.

### 8.3 Drafts

```sql
CREATE TABLE drafts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id TEXT NOT NULL,
  revision INTEGER NOT NULL,
  reply_es TEXT NOT NULL,
  translation_en TEXT,
  reason TEXT,
  status TEXT DEFAULT 'pending',
  model TEXT,
  usage_json TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  notified_at TEXT
);

CREATE INDEX idx_drafts_chat
ON drafts(chat_id, created_at);
```

Suggested statuses:

- `pending`
- `notified`
- `stale`
- `failed`

A draft marked `stale` must never subsequently be delivered as a current recommendation.

For V1, no approval or sending-state machinery is needed.

### Database handling

All insertions and revision increments that must occur together should use a SQLite transaction.

Create the database automatically on first startup.

Do not require a separate database service or manual table creation.

## 9. WhatsApp Event Handling

### FR-01: Approved Contact Filtering

The agent must process only the explicitly configured U.S. test contact.

Requirements:

- Ignore all other private chats.
- Ignore all group chats.
- Ignore statuses, broadcasts, and non-text messages.
- Ignore the owner's self-chat for AI generation.
- Never send messages to unapproved recipients.
- Do not log unrelated message contents.

Use stable identifiers resolved through the WhatsApp client. If identifiers differ across WhatsApp events, normalize them before comparing.

### FR-02: Incoming Messages

On receiving a valid incoming text message:

1. Resolve the chat ID.
2. Verify the contact is approved and enabled.
3. Insert the message into SQLite.
4. Ignore the event if its WhatsApp ID already exists.
5. Increment the conversation revision.
6. Invalidate existing pending drafts.
7. Reset the inactivity timer.
8. Schedule generation for the new revision.

### FR-03: Manual Outgoing Messages

When Mike manually sends a message to the test contact:

1. Store the outgoing message.
2. Increment the conversation revision.
3. Cancel any pending debounce timer.
4. Mark older drafts stale.
5. Invalidate any in-progress AI generation.
6. Do not generate another draft solely because Mike sent a message.

Generation may resume when a new incoming message arrives.

### FR-04: Self-Chat Exclusion

Draft notifications must never enter the conversation-processing pipeline.

The application must distinguish notifications generated by itself from test-contact messages.

No model requests may be triggered by self-chat draft delivery.

## 10. Debounce and Timing

### FR-05: 45-Second Inactivity Debounce

Use a configurable timer, defaulting to:

`DEBOUNCE_MS=45000`

The debounce represents the minimum period of silence after the most recent incoming message.

Every new incoming message must reset the timer.

### Example timeline

| Time | Event | Behavior |
|---|---|---|
| 00:00 | "Hola!" | Start timer |
| 00:07 | "Cómo estás?" | Reset timer |
| 00:19 | "Qué haces mañana?" | Reset timer |
| 01:04 | No further messages | Generate one draft |

The application must submit the complete recent conversation rather than the last message in isolation.

### FR-06: Single Generation per Contact

Allow at most one OpenRouter request in progress for the test contact.

Do not start overlapping model requests for the same conversation.

### FR-07: Incoming Messages During Generation

Consider this sequence:

1. Revision 12 begins generating.
2. Another message arrives.
3. SQLite advances to revision 13.
4. The original OpenRouter request completes.

Expected behavior:

- Revision 12's response is discarded.
- It must not be delivered.
- Revision 13 receives its own 45-second quiet period.
- Once the contact is quiet and the previous request has finished, the agent generates the latest draft.

If a debounce timer expires while an older generation is still running, retain the need to process the latest revision. Do not silently lose that event.

No additional queue infrastructure is required. An in-memory running flag, a debounce timer, and revision-aware scheduling are sufficient for one contact.

### FR-08: Restart Behavior

On application restart:

- Preserve existing database records.
- Preserve authenticated WhatsApp state.
- Do not send previously generated drafts automatically.
- Do not generate drafts for old messages merely because they exist in SQLite.
- Begin processing new live messages after connection becomes ready.

Historic-message backfilling is out of scope.

## 11. OpenRouter Integration

### FR-09: Model-Agnostic API Client

Use OpenRouter as the only model gateway.

Endpoint:

`POST https://openrouter.ai/api/v1/chat/completions`

Authentication:

`Authorization: Bearer OPENROUTER_API_KEY`

The selected model must be loaded from `.env`.

Do not hardcode a specific OpenAI, Anthropic, Google, or other provider model.

### FR-10: Model Request Inputs

Each request must include:

1. System instructions from `prompts/dating.md`.
2. Personal profile from `prompts/me.json`.
3. The latest conversation history, capped at `MAX_HISTORY_MESSAGES`.
4. The latest user-facing incoming message, already represented in the history.
5. Instructions to return a structured draft.

The system must preserve speaker roles in message history.

Prompt and profile text are trusted application configuration. WhatsApp messages are untrusted conversation data and must not override system instructions or sending policies.

### FR-11: Structured Output

Request this JSON structure:

```json
{
  "should_reply": true,
  "reply_es": "Todo bien, y tú qué planes tienes esta semana?",
  "translation_en": "All good. What plans do you have this week?",
  "reason": "Natural follow-up to continue the conversation."
}
```

Field requirements:

| Field | Type | Meaning |
|---|---|---|
| `should_reply` | Boolean | Whether any reply should be suggested |
| `reply_es` | String | Proposed Spanish WhatsApp reply |
| `translation_en` | String | English translation |
| `reason` | String | Brief internal explanation |

If `should_reply=false`, the reply fields may be empty. Do not deliver an outgoing draft.

Validate all returned data using `zod`.

For models supporting structured JSON Schema output, use that capability.

For models that do not, use a JSON instruction and validate locally.

Never send malformed, empty, or unvalidated output.

### FR-12: Timeouts and Errors

- Use a configurable 30-second request timeout.
- Handle API authorization failures.
- Handle rate limits.
- Handle malformed responses.
- Handle unavailable models.
- Do not retry indefinitely.
- Never automatically switch to a paid fallback model without explicit configuration.
- Record errors without exposing credentials or private conversation content.

A failed API request must not result in an automatic WhatsApp message to the test contact.

## 13. Draft Generation and Notification

### FR-16: Persist Draft

After OpenRouter returns a valid response:

1. Recheck the conversation revision.
2. Verify the contact is still enabled.
3. Verify no manual outgoing response invalidated the request.
4. Verify the response is valid.
5. Save the draft in SQLite.
6. Deliver the notification only if the draft is still current.

If any condition fails, discard the generated response or mark it stale.

### FR-17: Deliver Draft to WhatsApp Self-Chat

When `SELF_CHAT_NOTIFICATIONS=true`, deliver a formatted notification to the owner's own WhatsApp account.

Example:

```text
DRAFT #42 — US Test Contact

She said:
El viernes estoy libre.

Suggested reply:
Viernes me sirve. Un café en Laureles a las 6?

English:
Friday works for me. Coffee in Laureles at 6?

Reason:
She mentioned Friday availability.
```

Notification requirements:

- Identify the source conversation.
- Include the proposed Spanish reply.
- Include the English translation.
- Include an internal draft identifier.
- Do not include API metadata or debugging output.
- Do not forward the entire conversation history.
- Do not notify if `should_reply=false`.

### FR-18: Recipient Safety

The draft delivery module must resolve the owner's WhatsApp self-chat from the authenticated account.

It must never substitute the test contact when the self-chat cannot be resolved.

Do not allow an arbitrary recipient parameter to be passed from the LLM output.

If self-chat delivery fails:

- Keep the draft in SQLite.
- Log the failure.
- Display the draft in Terminal as a fallback.
- Do not send anything to the test contact.

The application must verify that self-chat delivery works with the actual connected WhatsApp account during manual testing.

### FR-19: Draft-Only Enforcement

In V1, automated sending to the test contact is prohibited.

This rule must be enforced through application code, not merely through prompt instructions.

Do not implement a generic AI-to-contact send function in this milestone.

The only permitted automated WhatsApp outbound operation is sending a draft notification to the authenticated account owner's verified self-chat.

## 14. Core Orchestration Logic

The core algorithm should resemble:

```text
ON INCOMING MESSAGE:

  if not approved test contact:
      ignore

  if not supported text:
      ignore

  save message by unique WhatsApp ID

  if duplicate:
      stop

  increment conversation revision

  mark old drafts stale

  reset 45-second timer


WHEN TIMER EXPIRES:

  if generation already running:
      preserve pending latest revision
      return

  read current revision

  load last 30 messages

  load master prompt

  load personal profile

  request structured reply from OpenRouter

  validate response

  if revision changed:
      discard result
      schedule latest revision if needed
      return

  if contact no longer enabled:
      discard result
      return

  if should_reply is false:
      finish without notification
      return

  save draft

  verify revision again

  notify owner through self-chat

  mark draft notified


ON MANUAL OUTGOING MESSAGE TO TEST CONTACT:

  save message

  increment revision

  cancel pending debounce

  invalidate previous drafts

  do not generate a draft


ON APPLICATION RESTART:

  initialize database

  reconnect existing WhatsApp session

  do not replay previous drafts

  listen for new messages
```

The implementation should preserve these semantics, even if the exact functions differ.

Use an in-memory per-contact timer and running-state flag. No Redis or background queue service is necessary.
